# AGENTS.md

Guidance for anyone (human or AI) working in this repo. Keep this file current when you change structure, commands, or conventions.

## Architecture

Monorepo, two packages:

- `server/` — Node + Express + TypeScript API (port 4000). PostgreSQL via `pg`, JWT auth, S3 presigned audio uploads (multer multipart fallback in dev/test), OpenAI Whisper transcription plus GPT transcript-based feedback. Entry: `server/src/index.ts`; app wiring in `server/src/app.ts`.
- `app/` — Expo React Native (SDK 57, expo-router, TanStack Query, expo-secure-store, expo-audio). All source lives under `app/src/` (routes in `app/src/app/`, shared code in `app/src/lib/` and `app/src/components/`); all tests live in `app/__tests__/`.

### Server module map (`server/src/`)

| Module | Responsibility |
| --- | --- |
| `index.ts` | Process entry: HTTP server, request/drain timeouts, startup dependency gates, janitor scheduling, graceful shutdown (SHUTDOWN_DRAIN_MS force timer, keep-alive severing, in-flight provider aborts) |
| `app.ts` | Express wiring: helmet/CORS/compression, client-version gate, limiter mounting order, routers, `/health` + `/ready`, 404 + error handler |
| `config.ts` | All env access, zod-validated at boot; exports the frozen-shape `config` object |
| `db.ts` | pg `Pool` (timeouts, size) plus the typed `QuestionRow`/`QUESTION_ROW_COLUMNS` layer for the questions table |
| `middleware.ts` | `HttpError` + `ApiErrorCode`, `requireAuth`, `validate`/`validated` (typed parsed bodies), `clientVersionGate`, central `errorHandler` (code defaults, uniform Retry-After) |
| `auth.ts` | Register/login/logout/change-password/forgot- and reset-password/profile-update/delete-account/data-export routes; bcrypt + JWT issuing; reset-token janitor |
| `mailer.ts` | Best-effort outbound mail (`MAIL_MODE=log` writes to the info log — refused in production, where `MAIL_MODE=webhook` is required and `MAIL_WEBHOOK_URL` must be HTTPS except loopback; `webhook` POSTs `{to, subject, text}` to `MAIL_WEBHOOK_URL` with a bounded timeout); never throws into a route |
| `diagnostic.ts` | Adaptive placement test: state locking, durable answer claims, binary-search finalization, confirmed restart |
| `practice.ts` | Practice question selection (SRS due-first revision/new/retention interleave), scored attempts, mastery + SRS upserts, CEFR level promotion, skip/history/stats routes, native-language mode |
| `assess.ts` | Paid AI pipeline: per-process AI semaphore, daily capacity reservations, one shared provider-call skeleton behind `assessSpeaking`/`assessNativeComprehension`, shutdown abort registry, usage janitor |
| `assessment-pipeline.ts` | Shared submission choreography for practice `/attempt`, `/attempt/native`, and diagnostic `/answer`: the middleware chain (S3-conditional cleanup + eligibility + paid limiters + dual-mode validation) and `runAssessmentSubmission` owning question fetch, idempotency-claim dance, audio gates, and the dual-finally cleanup; routes inject claim/assess/persist hooks |
| `idempotency.ts` | Durable per-request claims/replays for assessment POSTs (`assessment_requests`), replay janitor |
| `rate-limit.ts` | All limiters (per-IP, per-account, per-user, per-network daily) and the abort re-spend guard |
| `postgres-rate-limit-store.ts` | Shared fixed-window counter store (HMACed keys) + counter janitor |
| `janitor.ts` | Batched, advisory-lock-serialized DELETE helper every DB janitor runs through |
| `upload.ts` | Local multipart ingress: private disk storage, size/magic-byte gates, upload janitor |
| `audio-upload.ts` | S3 ingress: presigned POST grants, owned-key checks, object download/cleanup lifecycle |
| `audio-inspection.ts` | FFmpeg/ffprobe duration + stream-count gate with its own concurrency cap |
| `logger.ts` | pino + pino-http request logging |
| `metrics.ts` | Prometheus registry (prom-client): default node metrics, HTTP/provider-call histograms, pg-pool + AI/inspection slot gauges, shed-request and janitor counters; `GET /metrics` is mounted by app.ts only when `METRICS_ENABLED=true` (404 otherwise) and must be scraped privately |
| `transaction.ts` | Rollback/release helpers that keep pg-pool leases safe on failure paths |
| `schema-readiness.ts` | Migration-manifest, runtime-table, and question-inventory readiness checks |

Contract between them: camelCase JSON everywhere; auth = `Authorization: Bearer <jwt>`. Every error body is `{ error, code, ...extras }` with a stable machine-readable `code`, and any `retryAfterSeconds`/`retryAfterHours` extra is mirrored into a `Retry-After` header (seconds). **The response contract is additive-only**: fields are added, never renamed/removed/retyped — clients must tolerate unknown fields, and a change that cannot be additive requires raising `MIN_CLIENT_VERSION` so older clients get `426 CLIENT_UPGRADE_REQUIRED` instead of misparsing. The app advertises itself on every API request via `X-Client-Version: <expoConfig.version>` (omitted if the version is unset, and never sent on direct-to-S3 uploads), so the gate can actually retire old builds. Audio upload is two-step: the app calls `POST /uploads/audio-url` with the recording's content type and either gets a size-constrained `{mode:'s3', uploadUrl, uploadFields, audioKey, contentType, expiresIn, maxBytes}` grant — it submits the signed multipart form straight to S3, then POSTs JSON `{questionId, requestId, audioKey}` to the assessment endpoint — or `{mode:'direct'}` (dev/test without `S3_BUCKET`), where it posts multipart with file field `audio` + UUID text fields `questionId` and `requestId`. In both modes `requestId` must be reused when retrying one logical submission, and the assessment-endpoint response contract is identical. The app persists the upload stage and S3 key in secure storage so an interrupted handoff can reconcile the same logical request; if reconciliation hits the definitive "audio upload not found or expired" 400 (the server deletes submitted objects after failed assessments) and the local recording still exists, recovery performs one automatic re-upload per recovery cycle — fresh `audioKey`, same `requestId` — bounded by `MAX_S3_REUPLOADS = 1` alongside the existing resubmission backoff. The app validates every grant as hostile input and only uploads to genuine AWS S3 hosts (`*.amazonaws.com`); an S3-compatible non-AWS provider must relax that pin deliberately. The app derives its base URL from `EXPO_PUBLIC_API_URL` (fallback: LAN IP from Expo hostUri, then platform-specific emulator URLs).

## Commands

Server (`cd server`):

- `npm run db:setup` — local/initial setup: create DB if missing, run checksummed migrations, idempotently seed 600 questions (100 per CEFR level)
- `npm run db:migrate` / `npm run db:migrate:prod` — migration-only development / compiled production commands; production then runs `npm run db:catalog:prod` to publish the reviewed idempotent question catalog. Deploys must not run `db:setup` (`setup`/`seed` hard-refuse when `NODE_ENV=production`).
- `npm run dev` — tsx watch; needs `.env` (see `.env.example`); `MOCK_AI=true` avoids OpenAI calls
- `npm test` — vitest + supertest with enforced coverage thresholds against auto-created `ai_english_test` DB
- `npm run format:check` · `npm run lint` · `npm run typecheck` · `npm run build` · `npm test`
- `npm run mutation:lanes:verify` — read-only check that the server's mutation manifest assigns every non-catalog production TypeScript file exactly once and references only existing tests
- `RATE_LIMIT_ASSESS_MAX=100000 ASSESS_DAILY_CAP=100000 ASSESS_GLOBAL_DAILY_CAP=100000 ASSESS_IP_DAILY_CAP=100000 npm run dev` then `npm run smoke` — full e2e journey smoke test (needs relaxed limits)
- For the barrier-dispatched 10-user API journey, start a separate mock/direct-upload server with the full relaxed-limit recipe documented at the top of `server/scripts/concurrent-smoke.mjs`, then run `BASE_URL=http://localhost:4100 npm run smoke:concurrent`. Non-loopback targets require HTTPS and the explicit `ALLOW_NON_LOOPBACK_LOAD=true` safety opt-in. CI instead uses a single-server variant (no `BASE_URL`; the same relaxed-limit server on :4000 serves both `smoke` and `smoke:concurrent`, with the credential-budget knobs `RATE_LIMIT_LOGIN_ACCOUNT_MAX`/`RATE_LIMIT_FORGOT_EMAIL_MAX`/`RATE_LIMIT_PASSWORD_MAX` also relaxed).
- `npm run smoke:load1000` — barrier-dispatched 1000-user mixed-cohort journey (full/english-only/native-only/account flows plus error-path checks) against a mock/direct-upload server on a dedicated database; writes a per-user action ledger to `server/reports/load1000/`. `npm run verify:load1000` then reconciles `users`/`attempts`/`assessment_requests`/`practice_progress`/`diagnostic_state`/`assessment_usage`/`rate_limit_windows` against the newest ledger (row counts, per-user deep samples, cascade and anonymization checks). The client honors the contracted 503+Retry-After assess-semaphore backpressure and retries 5xx; assessment POSTs always reuse one `requestId` per logical submission.

App (`cd app`):

- `npx expo start` — run in Expo Go / simulator
- `npm run format:check` · `npm run lint` · `npm run typecheck` · `npm test` (with enforced coverage floors) · `npm run doctor`
- `npm run audit:ci` — reject new dependency advisories while the reviewed Expo/Metro upstream baseline remains
- `NODE_ENV=production EXPO_PUBLIC_API_URL=https://api.example.invalid npx expo export --platform ios` (and `android`) — production bundle validation

## Conventions

- **Migrations only for schema changes** — add `db/migrations/00N_name.sql`; never edit applied migration files.
- **Config** — all env access goes through `server/src/config.ts` (zod-validated at boot). Add new knobs there and in `.env.example`.
- **Validation** — every route validates body + params with zod via `validate()`; malformed UUIDs must 400, not 500.
- **Logging** — use the pino logger (`server/src/logger.ts`), never `console.*`; never log tokens, passwords, or secrets.
- **Errors** — throw `HttpError(status, message, code?)` or `HttpError(status, message, extra, code?)` with an `ApiErrorCode`; the central handler shapes the response, defaults missing codes by status family, and emits `Retry-After` for retry extras. Don't leak internals.
- **Rate limits** — new expensive endpoints must get a limiter in `server/src/rate-limit.ts`. Security-sensitive auth/login-account/password-account/register/assessment/assess-ip-daily/upload-grant counters use the shared PostgreSQL store in `server/src/postgres-rate-limit-store.ts`; keep namespaces stable across replicas and add migrations for store schema changes. The coarse global flood brake is configurable via `RATE_LIMIT_GLOBAL_STORE`: 'memory' (default) enforces a per-replica in-process budget and writes no counter rows; 'postgres' shares one cluster-wide budget (an upstream WAF/edge limit still owns volumetric floods). The login-account limiter runs after JSON parsing, HMACs normalized email keys, and refunds successful responses. Credential budgets (login-account, password-account) never reject at the middleware: they flag the request and the route still verifies the password, so only failures are throttled and a saturated budget cannot lock out the real owner. `POST /auth/forgot-password` layers a per-target-email budget (`forgot-email` namespace) on the same flag-don't-reject pattern atop the per-IP auth limiter: over-budget requests still answer the uniform 204 but silently skip issuing/sending. `POST /diagnostic/restart` has its own per-user PG-backed budget (`diagnostic-restart` namespace, passwordAccount-shaped knobs) that rejects outright with 429. Store `decrement`/`resetKey` are fail-safe by contract (express-rate-limit calls them fire-and-forget). `assess-ip-daily` bounds paid assessments per source IP per day so account re-registration cannot reset spend. The assess and assess-ip-daily limiters set `skipFailedRequests`, so ≥400 responses are refunded through the fail-safe `decrement` — but only while no paid work was spent: routes set `res.locals.assessmentCapacityReserved` via the `onCapacityReserved` assess hook once the daily-capacity reservation commits, and `requestWasSuccessful` then keeps the hit even on a later ≥400. Because express-rate-limit's close handler refunds aborted requests unconditionally, the `assessAbortGuard` middleware mounted after the two assessment limiters re-spends both hits when a client aborts after that reservation; the re-spend is window-guarded (`incrementWithinWindow` — an expired window is never rolled over into a fresh charge) and also fires at reservation time when the client has already disconnected, so a close-before-commit abort cannot escape with refunded hits. A saturated pool or counter-store brownout sheds requests as retryable 503 + Retry-After (never raw 500s), and a boot-time check errors loudly when `DB_POOL_MAX` leaves fewer than 3 server connections. S3 grants have a separate budget so grant issuance does not consume the paid assessment limiter.
- **Audio ingress** — production stores learner audio in S3 via size-constrained presigned POST forms (`server/src/audio-upload.ts`; `S3_BUCKET` required in production). Keys are `audio-uploads/{userId}/{uuid}.{ext}`, validated per-user before the API downloads them, and submitted objects are deleted after assessment. Production buckets also need a short lifecycle expiration for uploads abandoned before assessment submission. Local dev/test keeps the multer multipart flow (`server/src/upload.ts`); never make tests depend on real AWS. Startup and `/ready` must validate both configured `ffprobe` and `ffmpeg` executables. The duration gate first counts audio streams with ffprobe (machine-readable, over the same sandboxed `fd:` descriptor) and rejects anything but exactly one — do not replace this with `0:a?` into one PCM muxer, which only fails closed on some FFmpeg versions (8.x errors, 6.1 decodes) — and the MOV branch decodes with `-ignore_editlist 1` so a forged `elst` presentation window cannot shrink the measured audio. Keep both invariants so only duration-verified audio reaches the paid transcriber.
- **Money endpoints** — anything that calls OpenAI must go through the assess pipeline (daily cap + concurrency semaphore) — never call OpenAI directly from a route. Provider calls register their `AbortController` in assess.ts's shutdown registry so a deploy drain aborts them fast.
- **DB janitors** — periodic cleanup must go through `runExclusiveBatchedDelete` (`src/janitor.ts`): bounded ctid batches so backlogs never hold long row-locking DELETEs, and a per-janitor `pg_try_advisory_lock` so only one replica runs a tick.
- **Practice algorithm** — word bank is 100 questions per CEFR level, authored in per-level modules under `server/db/seed-data/` (aggregated by `server/db/seed-data.ts`; never hand-edit generated `seed.sql`). Per-word mastery lives in `practice_progress` (migrations 008/010; migration 011 tightens `srs_interval_index` to CHECK 0–4 and moves every remaining question FK to `ON DELETE RESTRICT`, matching 010's attempts rule): one English practice attempt scoring ≥ `MASTER_SCORE` (75, `server/src/practice.ts`) masters the word. Every scored attempt also updates the word's SRS schedule (`due_at`/`srs_interval_index`, intervals 1/3/7/21/60 days): fail (<60) → due now at index 0, pass-not-mastered → due in 1 day at index 1, mastery or retention pass → index+1 (clamped) with `due_at = now() + intervals[index]`. A mastered word demotes back to learning ONLY when a scored attempt on it fails below 60 — no other path downgrades mastery. Mastering a word can also promote the learner: inside the same transaction, when mastered words reach `ceil(0.85 × totalAtLevel)` and a next CEFR level exists, `users.cefr_level` advances and the attempt response carries `levelUp {from, to}` with `next`/`progress` from the new level (C2 never promotes). `GET /practice/question` interleaves revision (learning words, most overdue `due_at` first) with new words — a session opens with revision when one is due, then buckets alternate based on the last attempt's kind; when the level is exhausted, mastered words cycle back as retention revisions (due-first). `POST /practice/skip` parks a word (`skipped_until`, 7 days; zero-attempt row allowed) out of new/revision selection — retention ignores skips; when every word at the level is parked, selection falls back to the soonest-unparking skipped word so `/question` never dead-ends. Silence (empty transcript) is a free retry: no `attempts` row, no progress write, attempt counter unmoved. `POST /practice/attempt/native` (mother-tongue mode) only checks comprehension and returns a model English answer — it never writes `attempts`/`practice_progress`; Whisper's language is always pinned from `users.native_language`, never from the client.
- **Native media work** — every FFmpeg decode must acquire the fail-fast `AUDIO_INSPECTION_MAX_CONCURRENCY` slot before spawning and release it on every outcome; do not queue unbounded decoder work.
- **Password policy** — min 8, letter + number; mirrored client-side via `passwordPolicyError()` in `app/src/lib/password-policy.ts`. Keep both in sync.
- **Recorder** — `app/src/components/Recorder.tsx` is the single shared recording component (spec requirement); do not fork it per screen.
- **TypeScript strict** in both packages; zero type errors is the bar for any change.
- Tests: add vitest coverage for any new endpoint; keep coverage thresholds and `scripts/smoke.mjs` passing. App component/hook tests use `@testing-library/react-native` v14 (devDependency) — its `render`/`fireEvent`/`act` APIs are fully async and must be awaited.
- **Mutation testing** — both packages pin Stryker in `devDependencies` (jest runner and concurrency 2 for app; vitest runner and concurrency 1 for server because server tests share one database). The server mutation run must set an explicit-port loopback `TEST_DATABASE_URL` whose database name contains `mutation`, ends in `_test`, and differs from both the ordinary `ai_english_test` suite database and the configured application database (including `server/.env`); the guard rejects unsafe targets before destructive setup. `npm run mutation` covers every production TypeScript file in either package. Server executable API/database code is partitioned by `scripts/mutation-lanes.mjs` into 19 disjoint source/test lanes: `npm run mutation:code` validates that manifest, runs every lane sequentially even when an earlier lane is below the strict 100% detected-mutant threshold, and strictly merges the lane JSON/HTML into `reports/mutation/code/code.{json,html}` before returning a final nonzero status. All authored `db/seed-data.ts` + `db/seed-data/*.ts` literals remain a separate `stryker.catalog.config.json` campaign with the byte-for-byte catalog artifact test. Never run server code lanes concurrently against one database; each Stryker invocation recreates it. The weekly `mutation.yml` workflow runs server code and catalog as independent jobs so either report survives failure or timeout in the other, alongside the app campaign.

## Verification before calling work done

1. `cd server && npm run format:check && npm run lint && npm run typecheck && npm run build && npm test`
2. Smoke: server running with relaxed limits + `MOCK_AI=true` → `npm run smoke` exit 0
3. `cd app && npm run format:check && npm run lint && npm run typecheck && npm test && npm run doctor && npm run audit:ci`
4. In `app`, production-mode `expo export` for both `ios` and `android` with an explicit HTTPS `EXPO_PUBLIC_API_URL`
5. The server's full `npm audit --audit-level=high` must pass. In the app, `npm run audit:ci` is the authoritative reviewed-baseline gate; also record the raw `npm audit` result transparently.
6. When container files change, build and scan `server/Dockerfile` and exercise its healthcheck before release
7. For a full mutation campaign, run `cd app && npm run mutation`; then run `cd server && TEST_DATABASE_URL=postgres://localhost:5432/ai_english_mutation_test npm run mutation`. Record the executable-code and catalog results separately.
