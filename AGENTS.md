# AGENTS.md

Guidance for anyone (human or AI) working in this repo. Keep this file current when you change structure, commands, or conventions.

## Architecture

Monorepo, two packages:

- `server/` — Node + Express + TypeScript API (port 4000). PostgreSQL via `pg`, JWT auth, S3 presigned audio uploads (multer multipart fallback in dev/test), OpenAI Whisper transcription plus GPT transcript-based feedback. Entry: `server/src/index.ts`; app wiring in `server/src/app.ts`.
- `app/` — Expo React Native (SDK 57, expo-router, TanStack Query, expo-secure-store, expo-audio). All source lives under `app/src/` (routes in `app/src/app/`, shared code in `app/src/lib/` and `app/src/components/`); all tests live in `app/__tests__/`.

Contract between them: camelCase JSON everywhere; auth = `Authorization: Bearer <jwt>`. Every error body is `{ error, code, ...extras }` with a stable machine-readable `code`, and any `retryAfterSeconds`/`retryAfterHours` extra is mirrored into a `Retry-After` header (seconds). **The response contract is additive-only**: fields are added, never renamed/removed/retyped — clients must tolerate unknown fields, and a change that cannot be additive requires raising `MIN_CLIENT_VERSION` so older clients get `426 CLIENT_UPGRADE_REQUIRED` instead of misparsing. The app advertises itself on every API request via `X-Client-Version: <expoConfig.version>` (omitted if the version is unset, and never sent on direct-to-S3 uploads), so the gate can actually retire old builds. Audio upload is two-step: the app calls `POST /uploads/audio-url` with the recording's content type and either gets a size-constrained `{mode:'s3', uploadUrl, uploadFields, audioKey, contentType, expiresIn, maxBytes}` grant — it submits the signed multipart form straight to S3, then POSTs JSON `{questionId, requestId, audioKey}` to the assessment endpoint — or `{mode:'direct'}` (dev/test without `S3_BUCKET`), where it posts multipart with file field `audio` + UUID text fields `questionId` and `requestId`. In both modes `requestId` must be reused when retrying one logical submission, and the assessment-endpoint response contract is identical. The app persists the upload stage, S3 key, cancel intent, and recovery-POST count in secure storage so an interrupted handoff can reconcile the same logical request. A cancel after the assessment POST begins is durably marked before the transport is aborted: recovery may still deliver an already-committed result, but confirmed absence never creates new work. Recovery claims at most one automatic assessment POST across remounts; only the exact `AUDIO_UPLOAD_MISSING` 400 refunds that claim before the one allowed fresh-key re-upload. Automatic in-band 503 retry is restricted to `CAPACITY_BUSY`; recognized provider/server failures return the take for an explicit learner retry, while other received-response ambiguities poll without preserving an automatic POST budget. Completed server replays remain available for 48 hours, safely beyond the client's 25-hour automatic-recovery horizon. The app validates every grant as hostile input and only uploads to genuine AWS S3 hosts (`*.amazonaws.com`); an S3-compatible non-AWS provider must relax that pin deliberately. The app derives its base URL from `EXPO_PUBLIC_API_URL` (fallback: LAN IP from Expo hostUri, then platform-specific emulator URLs).

## Commands

Server (`cd server`):

- `npm run db:setup` — local/initial setup: create DB if missing, run checksummed migrations, idempotently seed 600 questions (100 per CEFR level)
- `npm run db:migrate` / `npm run db:migrate:prod` — migration-only development / compiled production commands; production then runs `npm run db:catalog:prod` to publish the reviewed idempotent question catalog. Deploys must not run `db:setup` (`setup`/`seed` hard-refuse when `NODE_ENV=production`).
- `npm run dev` — tsx watch; needs `.env` (see `.env.example`); `MOCK_AI=true` avoids OpenAI calls
- `npm test` — vitest + supertest with enforced coverage thresholds against auto-created `ai_english_test` DB
- `npm run format:check` · `npm run lint` · `npm run typecheck` · `npm run build` · `npm test`
- `npm run mutation:lanes:verify` — read-only check that the server's mutation manifest assigns every non-catalog production TypeScript file exactly once, references only existing tests, and accounts for every `tests/*.test.ts` file (assigned to a lane or documented with a reason in `intentionallyUnassignedTestFiles`)
- `RATE_LIMIT_ASSESS_MAX=100000 ASSESS_DAILY_CAP=100000 ASSESS_GLOBAL_DAILY_CAP=100000 ASSESS_IP_DAILY_CAP=100000 npm run dev` then `npm run smoke` — full e2e journey smoke test (needs relaxed limits)
- For the barrier-dispatched 10-user API journey, start a separate mock/direct-upload server with the full relaxed-limit recipe documented at the top of `server/scripts/concurrent-smoke.mjs`, then run `BASE_URL=http://localhost:4100 npm run smoke:concurrent`. Non-loopback targets require HTTPS and the explicit `ALLOW_NON_LOOPBACK_LOAD=true` safety opt-in. CI instead uses a single-server variant (no `BASE_URL`; the same relaxed-limit server on :4000 serves both `smoke` and `smoke:concurrent`, with the credential-budget knobs `RATE_LIMIT_LOGIN_ACCOUNT_MAX`/`RATE_LIMIT_FORGOT_EMAIL_MAX`/`RATE_LIMIT_PASSWORD_MAX` also relaxed).
- `npm run smoke:load1000` — barrier-dispatched 1000-user mixed-cohort journey (full/english-only/native-only/account flows plus error-path checks) against a mock/direct-upload server on a dedicated database; writes a per-user action ledger to `server/reports/load1000/`. `npm run verify:load1000` then reconciles `users`/`attempts`/`assessment_requests`/`practice_progress`/`diagnostic_state`/`assessment_usage`/`rate_limit_windows` against the newest ledger (row counts, per-user deep samples, cascade and anonymization checks). The client honors the contracted 503+Retry-After assess-semaphore backpressure and retries 5xx; assessment POSTs always reuse one `requestId` per logical submission.

App (`cd app`):

- `npx expo start` — run in Expo Go / simulator
- `npm run format:check` · `npm run lint` · `npm run typecheck` · `npm test` (with enforced coverage floors) · `npm run doctor`
- `npm run audit:ci` — reject new dependency advisories while the reviewed Expo/Metro upstream baseline remains
- `NODE_ENV=production EXPO_PUBLIC_API_URL=https://api.example.invalid npx expo export --platform ios` (and `android`) — production bundle validation

## Conventions

- **Migrations only for schema changes** — add `db/migrations/00N_name.sql`; never edit applied migration files.
- **Config** — all env access goes through `server/src/config.ts` (zod-validated at boot). Add new knobs there and in `.env.example`.
- **Validation** — every route validates body + params with zod via `validate()`; malformed UUIDs must 400, not 500.
- **Logging** — use the pino logger (`server/src/logger.ts`), never `console.*`; never log tokens, passwords, or secrets.
- **Errors** — throw `HttpError(status, message, code?)` or `HttpError(status, message, extra, code?)` with an `ApiErrorCode`; the central handler shapes the response, defaults missing codes by status family, and emits `Retry-After` for retry extras. Don't leak internals.
- **Rate limits** — new expensive endpoints must get a limiter in `server/src/rate-limit.ts`. Security-sensitive auth/login-account/password-account/register/assessment/assess-ip-daily/upload-grant counters use the shared PostgreSQL store in `server/src/postgres-rate-limit-store.ts`; keep namespaces stable across replicas and add migrations for store schema changes. The coarse global flood brake is configurable via `RATE_LIMIT_GLOBAL_STORE`: 'memory' (default) enforces a per-replica in-process budget and writes no counter rows; 'postgres' shares one cluster-wide budget (an upstream WAF/edge limit still owns volumetric floods). The login-account limiter runs after JSON parsing, HMACs normalized email keys, and refunds successful responses. Credential budgets (login-account, password-account) never reject at the middleware: they flag the request and the route still verifies the password, so only failures are throttled and a saturated budget cannot lock out the real owner. `POST /auth/forgot-password` layers a per-target-email budget (`forgot-email` namespace) on the same flag-don't-reject pattern atop the per-IP auth limiter: over-budget requests still answer the uniform 204 but silently skip issuing/sending. `POST /diagnostic/restart` has its own per-user PG-backed budget (`diagnostic-restart` namespace, passwordAccount-shaped knobs) that rejects outright with 429. Store `decrement`/`resetKey` are fail-safe by contract; response-contingent refunds must go through the wrapper's `decrementWithinWindow(key, observedResetAt)` so a late old-window response can never subtract a successor window's hit. `assess-ip-daily` bounds paid assessments per source IP per day so account re-registration cannot reset spend. The assess and assess-ip-daily wrappers refund ≥400 responses only while no paid work was spent: routes set `res.locals.assessmentCapacityReserved` via the `onCapacityReserved` assess hook once the daily-capacity reservation commits, and the finish predicate then keeps the hit even on a later ≥400. The wrappers also refund unfinished close/error transport failures; `assessAbortGuard`, mounted after both limiters, re-spends both exact-window hits when transport fails after that reservation, and the reservation hook does the same when the failure event arrived first. Both directions are window-identity guarded (`decrementWithinWindow`/`incrementWithinWindow`), so an expired or renewed row is never charged/refunded, and their atomic updates net to zero in either completion order. A saturated pool or counter-store brownout sheds requests as retryable 503 + Retry-After (never raw 500s), and a boot-time check errors loudly when `DB_POOL_MAX` leaves fewer than 3 server connections. S3 grants have a separate budget so grant issuance does not consume the paid assessment limiter.
- **Audio ingress** — production stores learner audio in S3 via size-constrained presigned POST forms (`server/src/audio-upload.ts`; `S3_BUCKET` required in production). Keys are `audio-uploads/{userId}/{uuid}.{ext}`, validated per-user before the API downloads them, and migration 013 binds each key to at most one durable assessment request. Only a fresh successful owner actively deletes; completed replays, rejected requests, and unbound submissions are retained for the mandatory short bucket lifecycle, because a replay deletion begun near the 48-hour tombstone expiry—or any ownership-check-then-delete for an unbound key—can race a newly bound request. The finalizer also preserves while any non-expired processing claim references the key and fails closed when ownership cannot be checked; an error after a client abort intentionally retains the object. Local dev/test keeps the multer multipart flow (`server/src/upload.ts`); never make tests depend on real AWS. Startup and `/ready` must validate both configured `ffprobe` and `ffmpeg` executables. The duration gate first counts audio streams with ffprobe (machine-readable, over the same sandboxed `fd:` descriptor) and rejects anything but exactly one — do not replace this with `0:a?` into one PCM muxer, which only fails closed on some FFmpeg versions (8.x errors, 6.1 decodes) — and the MOV branch decodes with `-ignore_editlist 1` so a forged `elst` presentation window cannot shrink the measured audio. Keep both invariants so only duration-verified audio reaches the paid transcriber.
- **Missing S3 objects** — both empty-body and NoSuchKey/NotFound/404 download failures must use the exact additive `AUDIO_UPLOAD_MISSING` error code. Recorder refunds its one durable recovery-POST claim and permits a fresh-key re-upload only for that code; generic validation 400s are terminal and must never trigger another object upload.
- **Money endpoints** — anything that calls OpenAI must go through the assess pipeline (daily cap + concurrency semaphore) — never call OpenAI directly from a route. Provider calls register their `AbortController` in assess.ts's shutdown registry so a deploy drain aborts them fast.
- **DB janitors** — periodic cleanup must go through `runExclusiveBatchedDelete` (`src/janitor.ts`): bounded ctid batches (at most 10 per tick) so backlogs never hold long row-locking DELETEs or monopolize a pool lease indefinitely, and a per-janitor `pg_try_advisory_lock` so only one replica runs a tick.
- **Practice algorithm** — word bank is 100 questions per CEFR level, authored in per-level modules under `server/db/seed-data/` (aggregated by `server/db/seed-data.ts`; never hand-edit generated `seed.sql`). Per-word mastery lives in `practice_progress` (migrations 008/010; migration 011 tightens `srs_interval_index` to CHECK 0–4 and moves every remaining question FK to `ON DELETE RESTRICT`, matching 010's attempts rule): one English practice attempt scoring ≥ `MASTER_SCORE` (75, `server/src/practice.ts`) masters the word. Every scored attempt also updates the word's SRS schedule (`due_at`/`srs_interval_index`, intervals 1/3/7/21/60 days): fail (<60) → due now at index 0, pass-not-mastered → due in 1 day at index 1, mastery or retention pass → index+1 (clamped) with `due_at = now() + intervals[index]`. A mastered word demotes back to learning ONLY when a scored attempt on it fails below 60 — no other path downgrades mastery. Mastering a word can also promote the learner: inside the same transaction, when mastered words reach `ceil(0.85 × totalAtLevel)` and a next CEFR level exists, `users.cefr_level` advances and the attempt response carries `levelUp {from, to}` with `next`/`progress` from the new level (C2 never promotes). `levelUp` is attached ONLY when that attempt's own mastery triggered the promotion — a rival session's promotion landing mid-assessment yields the attempt's normal outcome shape (with `next`/`progress` read from the new level where the shape allows), and the app parser rejects `levelUp` on non-mastering attempts. `GET /practice/question` interleaves revision (learning words, most overdue `due_at` first) with new words — a session opens with revision when one is due, then buckets alternate based on the last attempt's kind; when the level is exhausted, mastered words cycle back as retention revisions (due-first). `POST /practice/skip` parks a word (`skipped_until`, 7 days; zero-attempt row allowed) out of new/revision selection — retention ignores skips; when every word at the level is parked, selection falls back to the soonest-unparking skipped word so `/question` never dead-ends; a scored attempt clears the park (`skipped_until` is nulled by the progress upsert). Silence (empty transcript) is a free retry: no `attempts` row, no progress write, attempt counter unmoved. `POST /practice/attempt/native` (mother-tongue mode) only checks comprehension and returns a model English answer — it never writes `attempts`/`practice_progress`; Whisper's language is always pinned from `users.native_language`, never from the client.
- **Native media work** — every FFmpeg decode must acquire the fail-fast `AUDIO_INSPECTION_MAX_CONCURRENCY` slot before spawning and release it on every outcome; do not queue unbounded decoder work.
- **Password policy** — min 8, letter + number; mirrored client-side via `passwordPolicyError()` in `app/src/lib/password-policy.ts`. Keep both in sync.
- **Recorder** — `app/src/components/Recorder.tsx` is the single shared recording component (spec requirement); do not fork it per screen. OS backgrounding deliberately discards a held, unsubmitted take (no unsubmitted audio persists outside the documented recovery stages; the native mount-time cache janitor removes crash-orphaned `recording-*` files while protecting every recorder URI created by the current process). Expo `RecordingStatus` completion/error/reset events are authoritative; the scoped 200 ms status poll exists only for live duration/metering and must never treat `canRecord=true` pause as completion. Async ownership uses per-operation tokens, durable cancel/recovery counters, and the module-level serialized audio-session owner/release promise—never replace these with an ownerless boolean or an uncoordinated `setAudioModeAsync` call.
- **Frontend async identity** — account-scoped async screen work captures an Auth `SessionLease` and validates it after awaits before committing user/cache/navigation/PII side effects. Auth owns synchronous token/user/epoch refs, so render-time `sessionVersion` checks alone are not an adequate logout/password-rotation fence. Settings and credential mutations also synchronously lock GO_BACK/header gestures while active; singleton navigation uses a ref latch or `router.navigate`, never an unguarded `router.push` from a reusable tap target.
- **Frontend durable handoffs** — a new assessment must claim pending metadata through the generation-fenced atomic `ensurePendingAssessment`; never rebuild the old `loadPendingAssessment()` → conditional `savePendingAssessment()` split. Only a matching fresh `prepared` record may advance to upload. Unconditional auth cleanup advances the generation synchronously so pre-cleanup creators cannot write after logout.
- **Frontend retries/paging** — repeated manual GET retries join the active request with `cancelRefetch: false`; paged UI walkers must reject repeated/cyclic cursors and retain an explicit page bound. Do not introduce retry, polling, or effect loops without an attempt, lease, page, or time bound and an unmount/abort exit.
- **TypeScript strict** in both packages; zero type errors is the bar for any change.
- Tests: add vitest coverage for any new endpoint; keep coverage thresholds and `scripts/smoke.mjs` passing. App component/hook tests use `@testing-library/react-native` v14 (devDependency) — its `render`/`fireEvent`/`act` APIs are fully async and must be awaited.
- **Mutation testing** — both packages pin Stryker in `devDependencies` (jest runner and concurrency 2 for app; server executable-code lanes use vitest concurrency 1 because their tests share one database, while the pure read-only catalog oracle uses bounded concurrency 4 with one Vitest worker per isolated Stryker child). The app lane runner writes `${lane}.provenance.json` beside each lane report; `scripts/mutation-provenance.mjs` fingerprints every production source plus the mutation toolchain/runtime/environment and that lane's owning tests. A partial app run may merge retained reports only when every sidecar and every report-embedded source/test body still match current inputs; missing or stale provenance fails closed. Any production-source or shared-tooling change requires the full app campaign, while a test-only change requires rerunning every lane that owns that test. Reviewed app equivalences also pin every expected mutant's exact Stryker start/end location, so source drift and same-line survivor swaps fail closed; refresh those spans only from a fresh full campaign after re-reviewing the survivors. Duplicate lane requests are rejected, and each package's root `.mutation-campaign.lock` prevents independent processes from colliding even with different report directories; the server code, catalog, and standalone merge writers share the server-root lock. Locks are never reclaimed automatically: after interruption—or when a Stryker coordinator ends from a signal—the runner deliberately preserves the lock; verify that neither the recorded parent PID nor an orphan Stryker child is alive before manual removal. The server mutation run must set an explicit-port loopback `TEST_DATABASE_URL` whose database name contains `mutation`, ends in `_test`, and differs from both the ordinary `ai_english_test` suite database and the configured application database (including `server/.env`); the guard rejects unsafe targets before destructive setup. `npm run mutation` covers every production TypeScript file in either package; the server wrapper always executes code and catalog sequentially and aggregates their final status instead of short-circuiting catalog after a code failure. Server executable API/database code is partitioned by `scripts/mutation-lanes.mjs` into 19 disjoint source/test lanes: `npm run mutation:code` validates that manifest, clears every old lane artifact even for a programmatic subset, runs requested lanes sequentially even when an earlier lane is below the strict 100% detected-mutant threshold, and strictly merges only a complete current set into `reports/mutation/code/code.{json,html}` before returning a final nonzero status. Every expected executable source and runtime catalog source must report at least one mutant. The server runner writes report-bound `${lane}.provenance.json` sidecars that fingerprint all non-ignored backend workspace inputs, installed mutation tools, resolved Stryker config, Node runtime, and a secret-free hash of behavior-affecting environment; merge revalidates sidecars plus embedded production/test bodies before and after canonical writes. All authored `db/seed-data.ts` + `db/seed-data/*.ts` literals remain a separate `stryker.catalog.config.mjs` campaign with the byte-for-byte catalog artifact test. Its wrapper writes to a staging directory, validates the exact oracle-test source and catalog provenance, then publishes HTML/provenance before `catalog.json` as the commit marker; failed, stale, or invalid publication removes every canonical catalog artifact. Never run server code lanes concurrently against one database; each Stryker invocation recreates it. The weekly `mutation.yml` workflow runs server code and catalog as independent jobs so either report survives failure or timeout in the other, alongside the app campaign.

## Verification before calling work done

1. `cd server && npm run format:check && npm run lint && npm run typecheck && npm run build && npm test`
2. Smoke: server running with relaxed limits + `MOCK_AI=true` → `npm run smoke` exit 0
3. `cd app && npm run format:check && npm run lint && npm run typecheck && npm test && npm run doctor && npm run audit:ci`
4. In `app`, production-mode `expo export` for both `ios` and `android` with an explicit HTTPS `EXPO_PUBLIC_API_URL`
5. The server's full `npm audit --audit-level=high` must pass. In the app, `npm run audit:ci` is the authoritative reviewed-baseline gate; also record the raw `npm audit` result transparently.
6. When container files change, build and scan `server/Dockerfile` and exercise its healthcheck before release
7. For a full mutation campaign, run `cd app && npm run mutation`; then run `cd server && TEST_DATABASE_URL=postgres://localhost:5432/ai_english_mutation_test npm run mutation`. Record the executable-code and catalog results separately.
