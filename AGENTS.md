# AGENTS.md

Guidance for anyone (human or AI) working in this repo. Keep this file current when you change structure, commands, or conventions.

## Architecture

Monorepo, two packages:

- `server/` — Node + Express + TypeScript API (port 4000). PostgreSQL via `pg`, JWT auth, S3 presigned audio uploads (multer multipart fallback in dev/test), OpenAI Whisper transcription plus GPT transcript-based feedback. Entry: `server/src/index.ts`; app wiring in `server/src/app.ts`.
- `app/` — Expo React Native (SDK 57, expo-router, TanStack Query, expo-secure-store, expo-audio). All source lives under `app/src/` (routes in `app/src/app/`, shared code in `app/src/lib/` and `app/src/components/`); all tests live in `app/__tests__/`.

Contract between them: camelCase JSON everywhere; auth = `Authorization: Bearer <jwt>`. Every error body is `{ error, code, ...extras }` with a stable machine-readable `code`, and any `retryAfterSeconds`/`retryAfterHours` extra is mirrored into a `Retry-After` header (seconds). **The response contract is additive-only**: fields are added, never renamed/removed/retyped — clients must tolerate unknown fields, and a change that cannot be additive requires raising `MIN_CLIENT_VERSION` so older clients get `426 CLIENT_UPGRADE_REQUIRED` instead of misparsing. Production has a hard `1.1.1` floor for the diagnostic-run-aware mobile contract; later incompatible releases must raise both the app version and that production floor. When the gate is enabled, missing/malformed `X-Client-Version` is also rejected on product routes; `/health`, `/ready`, `/metrics`, and the explicit privacy/account exits remain exempt (including one trailing slash). `GET /client-config` is deliberately NOT exempt: it is neither an operational probe nor a privacy exit, and any first-party 426 — including one there — latches the app's upgrade modal, so fail-fast preserves the forced-upgrade outcome. The API is native-app-only by default: with `CORS_ORIGINS` empty the server grants no browser origins at all (no `Access-Control-Allow-Origin` on preflight or responses), which is the intended posture for the mobile client; a future web client must configure explicit origins rather than rely on a permissive default. The app advertises itself on every API request via `X-Client-Version: <expoConfig.version>` (never sent on direct-to-S3 uploads). Audio upload is two-step: the app calls `POST /uploads/audio-url` with `{contentType,assessmentEndpoint}` and either gets an endpoint-echoing, size-constrained `{mode:'s3', assessmentEndpoint, uploadUrl, uploadFields, audioKey, contentType, expiresIn, maxBytes}` grant — it submits the signed multipart form straight to S3, then POSTs JSON `{questionId, requestId, retainRecording, audioKey}` for diagnostic or `{questionId, requestId, cycleId, retainRecording, audioKey}` for practice to the same assessment endpoint — or endpoint-echoing `{mode:'direct',assessmentEndpoint}` (dev/test without the split S3 buckets), where it posts multipart with file field `audio` + UUID text fields `questionId`/`requestId`, boolean-string `retainRecording`, and the practice-only `cycleId`. `retainRecording` is optional for backward compatibility and defaults to `true` only when an older client omits it; the current app always sends the learner's explicit, default-off per-take choice. The server maps `/diagnostic/answer` to the diagnostic bucket and both practice endpoints to the practice bucket; clients never send bucket names. Keys are scoped as `audio-uploads/{diagnostic|practice}/{userId}/{uuid}.{ext}` and must agree with the durable endpoint. In both modes `requestId` must be reused when retrying one logical submission, and the assessment-endpoint response contract is identical. The app persists the upload stage, S3 key, retention choice, cancel intent, and recovery-POST count in secure storage so an interrupted handoff can reconcile the same logical request. A cancel after the assessment POST begins is durably marked before the transport is aborted: recovery may still deliver an already-committed result, but confirmed absence never creates new work. Recovery claims at most one automatic assessment POST across remounts; only the exact `AUDIO_UPLOAD_MISSING` 400 refunds that claim before the one allowed fresh-key re-upload. Known-offline recovery parks without consuming its five-minute polling window or clearing the handoff, and reconnect starts a fresh bounded window. Automatic in-band 503 retry is restricted to `CAPACITY_BUSY`; recognized provider/server failures return the take for an explicit learner retry, while other received-response ambiguities poll without preserving an automatic POST budget. Completed server replays remain available for 48 hours, safely beyond the client's 25-hour automatic-recovery horizon; delivered-feedback pointers expire conservatively from the original handoff time and terminal 404/incompatible results are conditionally retired. The app validates every grant as hostile input and only uploads to genuine AWS S3 hosts (`*.amazonaws.com`); an S3-compatible non-AWS provider must relax that pin deliberately. The app derives its base URL from `EXPO_PUBLIC_API_URL` (fallback: LAN IP from Expo hostUri, then platform-specific emulator URLs).

Migrations 022/023 and migration 024 are enforced non-rolling cutovers: first remove every older replica from traffic and drain in-flight requests/provider work, then apply migrations (and only then publish the catalog) before starting current replicas. ## Conventions

- **Migrations only for schema changes** — add `db/migrations/00N_name.sql`; never edit applied migration files. `db/schema-cutover.ts` owns the exact migration-023 and migration-024 manifest-fence identities shared by migration tooling, preflight, and runtime readiness; each SQL literal must stay byte-for-byte aligned. The fences intentionally sort before `001`, forcing pre-cutover readiness code out of service, so do not treat them as unknown ordinary migrations or remove them during later additive deploys.
- **Config** — all env access goes through `server/src/config.ts` (zod-validated at boot). Add new knobs there and in `.env.example`.
- **Validation** — every route validates body + params with zod via `validate()`; malformed UUIDs must 400, not 500.
- **Logging** — use the pino logger (`server/src/logger.ts`), never `console.*`; never log tokens, passwords, or secrets.
- **Errors** — throw `HttpError(status, message, code?)` or `HttpError(status, message, extra, code?)` with an `ApiErrorCode`; the central handler shapes the response, defaults missing codes by status family, and emits `Retry-After` for retry extras. Don't leak internals.
- **Rate limits** — new expensive endpoints must get a limiter in `server/src/rate-limit.ts`. Security-sensitive auth/login-account/password-account/register/assessment/assess-ip-daily/upload-grant counters use the shared PostgreSQL store in `server/src/postgres-rate-limit-store.ts`; keep namespaces stable across replicas and add migrations for store schema changes. Namespaces are config-independent BY DESIGN (semantic names like `login-account`, never embedding window/max values): a knob change must not silently abandon in-flight windows mid-brute-force, and divergent-env replicas during a rolling deploy must share one budget (deploying the config-independent namespaces itself was a deliberate one-time counter reset). The coarse global flood brake is configurable via `RATE_LIMIT_GLOBAL_STORE`: 'memory' (default) enforces a per-replica in-process budget and writes no counter rows; 'postgres' shares one cluster-wide budget (an upstream WAF/edge limit still owns volumetric floods). The login-account limiter runs after JSON parsing, HMACs normalized email keys, and refunds successful responses. Credential budgets (login-account, password-account) never reject at the middleware: they flag the request and the route still verifies the password, so only failures are throttled and a saturated budget cannot lock out the real owner. Their route-thrown 429s carry a `retryAfterSeconds` extra equal to the CONSTANT window length — never the remaining time — so the hint cannot be used to pace retries: a fixed value leaks only deployment config while honest users learn their maximum wait. (Middleware-rejected limiter 429s keep express-rate-limit's own remaining-time `Retry-After`, which is safe there because those budgets key the caller's IP/user, not a victim's credential.) `POST /auth/forgot-password` layers a per-target-email budget (`forgot-email` namespace) on the same flag-don't-reject pattern atop the per-IP auth limiter: over-budget requests still answer the uniform 204 but silently skip issuing/sending. `POST /auth/register` layers a per-target-email budget (`register-email` namespace, silent headers like the other email-keyed budgets) that rejects with a uniform 429 once one address is probed past `RATE_LIMIT_REGISTER_EMAIL_MAX`, bounding distributed EMAIL_TAKEN enumeration; successful registrations refund their hit. The per-IP register budget refunds pure validation 400s (zod or JSON-parse rejections) through the same exact-window refund wrapper — a 400 creates no account and never reaches the EMAIL_TAKEN oracle, so one buggy or impatient client behind a shared NAT cannot burn the whole network's signup budget on form errors — while 201 successes (bulk creation), 409 EMAIL_TAKEN probes (enumeration), 413 oversized bodies (flooding), and 429s themselves still count. `POST /diagnostic/restart`, `DELETE /recordings`, and `DELETE /recordings/:id` have independent per-user PG-backed budgets (`diagnostic-restart`, `recording-bulk-delete`, and `recording-delete` namespaces) using the passwordAccount-shaped knobs and reject outright with 429. Counter keys are HMACed with a domain-separated subkey of `RATE_LIMIT_HASH_SECRET` (falling back to a derived JWT_SECRET subkey — rotating JWT_SECRET alone resets every window once). Rejecting limiters keep `standardHeaders: true`, which is what emits `Retry-After` on 429s under express-rate-limit 8. Store `decrement`/`resetKey` are fail-safe by contract; response-contingent refunds must go through the wrapper's `decrementWithinWindow(key, observedResetAt)` so a late old-window response can never subtract a successor window's hit. `assess-ip-daily` bounds paid assessments per source IP per day so account re-registration cannot reset spend. The assess and assess-ip-daily wrappers refund ≥400 responses only while no paid work was spent: routes set `res.locals.assessmentCapacityReserved` via the `onCapacityReserved` assess hook once the daily-capacity reservation commits, and the finish predicate then keeps the hit even on a later ≥400. The two aborts that can follow the reservation commit but provably precede any provider call (the post-commit shutdown re-check and a missing OpenAI key) run in reverse: they best-effort DELETE exactly the just-inserted `assessment_usage` row and clear the latch via the `onCapacityReservationUndone` hook so the learner neither loses an allowance unit nor keeps limiter hits for work that never reached the provider; a failed undo keeps the reservation (fail-safe retention). The wrappers also refund unfinished close/error transport failures; `assessAbortGuard`, mounted after both limiters, re-spends both exact-window hits when transport fails after that reservation, and the reservation hook does the same when the failure event arrived first. Both directions are window-identity guarded (`decrementWithinWindow`/`incrementWithinWindow`), so an expired or renewed row is never charged/refunded, and their atomic updates net to zero in either completion order. A saturated pool or counter-store brownout sheds requests as retryable 503 + Retry-After (never raw 500s), and a boot-time check errors loudly when `DB_POOL_MAX` leaves fewer than 3 server connections. PostgreSQL lock-timeout (55P03) and statement-timeout (57014 with the statement-timeout message) errors shed through the same retryable 503 `POOL_SATURATED` path — a wedged hot-path lock is database backpressure, not an application fault — while user-initiated query cancellations keep the generic 500. S3 grants have a separate budget so grant issuance does not consume the paid assessment limiter.
- **Audio ingress and retained recordings** — production stores learner audio in versioned, private, split diagnostic/practice S3 buckets via size-constrained presigned POST forms (`server/src/audio-upload.ts`; bucket names must differ).
