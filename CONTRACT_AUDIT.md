# Frontend/API/Database Contract Audit

Audit snapshot: 2026-08-24 (America/Phoenix)

This report traces every mounted backend method/path contract, every API call used by the mobile app, the relevant PostgreSQL or provider contacts, and the data returned across each boundary. It combines code review, automated tests, and a controlled live AWS S3/OpenAI acceptance run; real mail delivery remains deferred.

## Outcome

- The server defines 25 method/path endpoint contracts: 24 are always mounted and `GET /metrics` is mounted only when metrics are enabled. The inventory comprises 3 operational endpoints, 10 auth endpoints, 1 assessment-status endpoint, 3 diagnostic endpoints, 7 practice endpoints, and 1 upload-grant endpoint.
- The app uses the 22 non-operational JSON/multipart endpoints. It also performs one direct, presigned multipart POST to AWS S3.
- Every app-used API success contract has a runtime parser or an exact no-content status check in the app. `server/tests/frontend-contract.test.ts` additionally drives real Express routes against the PostgreSQL test database and passes their success bodies through the app's actual pure parsers.
- Assessment responses stored in `assessment_requests.response_body` are validated by context both before storage and before replay. Question inventory is bounded and runtime-validated before readiness succeeds.
- The configured local development catalog exactly matches the authored catalog: 600 of 600 rows, exactly 100 per CEFR level, with zero missing, changed, or extra rows at this snapshot.
- The configured local development database and the test database both have migrations 001-015 applied. The strengthened preflight passed immediately before and after migration 015, and `/ready` returned 200 during the final mock/direct-upload smoke.
- A controlled 80-assertion live acceptance exercised both private S3 buckets plus real Whisper/GPT calls for diagnostic, English practice, and native practice. Real mail delivery, delayed S3 lifecycle expiration, and broader model-quality benchmarking remain explicitly deferred.
- Final mutation publication is complete. The app's strict 18-lane merge has current provenance and zero unexplained or stale mutants. The server's 19 executable lanes and separate catalog oracle also have current provenance and passed their strict gates.

## Shared public shapes

- `User`: `{id, name, email, nativeLanguage, cefrLevel, diagnosticCompleted}`.
- `Question`: `{id, cefrLevel, promptWord, questionText}`.
- `PracticeProgress`: `{masteredCount, learningCount, totalAtLevel, dueCount?}`.
- `PracticeQuestionPayload`: `{question, kind:'new'|'revision', progress}`.
- `AuthEnvelope`: `{token, user}`.
- `UserEnvelope`: `{user}`.
- Error envelope: `{error, code, ...safeExtras}`.

The response contract is additive-only. App parsers accept unknown additive fields but reject missing, retyped, inconsistent, oversized, or impossible required fields.

Every bearer endpoint also reads `users` through `requireAuth`, even when its inventory row lists only the route's business tables. Every non-operational endpoint passes the coarse global limiter; that limiter touches `rate_limit_windows` only when its optional PostgreSQL store is enabled.

## Database-to-backend and runtime-validation guarantees

1. **Schema provenance.** Applied migrations are checksummed. Startup and `/ready` compare the packaged migration prefix to `schema_migrations`; a missing or changed packaged migration fails readiness.
2. **Question rows.** `question-inventory.ts` performs a bounded 601-row scan and requires exactly 100 well-formed, app-parseable questions at each of A1-C2. It validates each public question ID with the app's strict RFC-4122 UUID pattern, checks prompt/question lengths, all four translations, and exactly three bounded `{en,native}` examples. The same validator is shared by preflight and readiness.
3. **Bounded readiness cost.** A successful production-pool inventory scan is cached for 60 seconds. Simultaneous cache misses join one in-flight validation instead of transferring/parsing the catalog repeatedly. Migration-manifest, required-table, and configured-audio checks still execute on every probe, and failed inventory checks are not cached. Injected query adapters bypass the process cache so tests/deployment seams cannot bless another database.
4. **Attempt invariants.** Migration 014 adds database checks for diagnostic attempt numbers 1-5, practice attempt numbers 1-3, and `passed = (score >= 60)`. Both the configured development database and test database have this migration.
5. **Persisted public strings.** Migration 015 rejects user names, user emails, and attempt feedback that are blank under the exact ECMAScript whitespace/line-terminator set used by JavaScript `trim()`, including tabs, NBSP, BOM, and Unicode spaces that PostgreSQL's one-argument `btrim` misses. Deployment preflight applies the same rules before migration validation so legacy violations fail with repair guidance rather than during DDL.
6. **Durable response JSONB.** `validatedAssessmentResponse(context,response)` applies a context-specific Zod union before completion storage and again before completed replay/status responses. It enforces score flags, attempt branches, next-question/progress structure, promotion adjacency, string bounds, and native silence/spoken variants. Invalid stored JSON fails closed as `500 INTERNAL` and is never sent as a learner result.
7. **Explicit projections.** Routes alias database snake_case to public camelCase and select explicit question/export/history fields. Authentication responses are built through one `toUserJson` projection and never include `password_hash` or `token_version`.
8. **Frontend validation.** `app/src/lib/types.ts` validates every structured success payload used for UI decisions. Export attempt objects intentionally retain server fidelity rather than stripping fields; safety there is supplied by the server's explicit export projection, bounded page parser, account-pinned cursor walk, and session lease.
9. **Transactions and ownership.** Registration, password reset, diagnostic state, assessment claims, attempts, mastery/SRS, promotion, and relevant cleanup use transactions/row locks and ownership tokens. Concurrency and rollback tests compare API results with persisted rows.
10. **Known query boundary.** Ordinary PostgreSQL query results are not universally parsed through Zod at every query call. Their guarantees come from migrations, explicit SQL projections/types, startup inventory checks, route assertions, and the app's final runtime parsers. Assessment replay and question inventory receive the additional server runtime validation described above.
11. **Known readiness boundary.** `/ready` proves the checksummed migration ledger/prefix, required `rate_limit_windows` table, configured audio tools, and exact question inventory (subject to the documented 60-second successful-result cache). It does not introspect every route-used table, column, index, or constraint through `pg_catalog`; manual post-migration DDL drift could retain a valid ledger and remain undetected until a query fails. The live inspection below is local-development evidence, not a production/staging database or TLS check.
12. **Known export-cache boundary.** Settings deletes its timestamped cache export in `finally`, but process death cannot run that cleanup and there is no stale-export janitor. A crash during a long export can leave a partial PII-bearing `.json` file until OS cache eviction; timestamp reuse also creates a low-probability overwrite risk. A future hardening step is UUID-named `.partial` files, atomic rename after the closing suffix, and bounded stale-prefix cleanup.

## Error, version, timeout, and retry contracts

- Every API error response is JSON `{error,code,...safeExtras}`. The central handler assigns a stable `ApiErrorCode` when a route does not provide a more specific one and hides unexpected internals.
- The app only trusts allowlisted machine codes and bounded retry values. It never displays the server/provider `error` text directly; localized safe copy comes from `userMessageForError`.
- `retryAfterSeconds` and `retryAfterHours` are mirrored into the standard `Retry-After` header in seconds. The app accepts bounded hints only for the contracted 429/503/in-flight cases. Assessment recovery does not blindly retry arbitrary errors.
- `CAPACITY_BUSY` is the only automatic in-band 503 retry for a submission. Daily/network limits and provider failures require their documented wait or explicit learner retry. Request IDs remain stable across ambiguous retries.
- Every API fetch sends `X-Client-Version` from `app/app.json` when configured. Multipart requests to the API send it too; direct S3 uploads deliberately do not. Versions below `MIN_CLIENT_VERSION` receive `426 CLIENT_UPGRADE_REQUIRED` before rate-limit/body work. The expanded smoke client now sends the actual app version.
- Authenticated API redirects fail closed (`redirect:'error'`) so a bearer token cannot follow a deployment redirect to another origin.
- JSON requests and response-body reads have bounded timeouts. Audio requests have a larger bounded budget and caller abort propagation.
- App helpers for no-content mutations require exact status 204; a different 2xx is treated as an invalid server response rather than silently accepted.
- Successful and router-handled auth/diagnostic/practice/upload responses are `Cache-Control: no-store`, except localized help, which is `private, no-cache`, varies on Authorization, and uses a payload-specific ETag. Upstream client-version, global-limiter, credential-limiter, or JSON-parser rejections occur before router cache middleware and are not guaranteed that router header.
