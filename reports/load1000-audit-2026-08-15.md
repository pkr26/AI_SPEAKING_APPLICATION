# 1000-User End-to-End Load Audit & Database Reconciliation — 15 August 2026

Point-in-time companion to `AUDIT_REPORT.md`. Scope: full frontend↔backend contract
map, a barrier-dispatched 1000-user mixed-action end-to-end run against the real
Express server (mock AI, direct upload), and a row-for-row reconciliation of the
PostgreSQL database against the client-recorded action ledger.

## Harness

- Server: compiled `dist/src/index.js`, `MOCK_AI=true`, direct upload, `DB_POOL_MAX=100`,
  `AI_MAX_CONCURRENCY=100`, all rate limits/daily caps relaxed, `UV_THREADPOOL_SIZE=32`,
  dedicated database `ai_english_load1000` (fresh: 9 migrations + 600-question catalog).
- New scripts (registered as npm scripts):
  - `npm run smoke:load1000` → `server/scripts/load-1000.mjs`: 1000 virtual users,
    barrier-dispatched phases (true simultaneity — register/login/diagnostic phases
    overlapped all 1000 clients within a ≤41 ms dispatch spread), mixed cohorts:
    40% full journey (help+ETag, English retry loop, progress, native attempt,
    status poll, idempotent replay, export), 30% English-only, 20% native-only,
    5% change-password + token-revocation checks, 5% export + account deletion;
    survivors then run error-path checks (wrong password, malformed UUID, missing
    token, hostile grant content type, unknown requestId). The client honors the
    contracted `503 + Retry-After` assess backpressure and retries 5xx/transport
    errors, always reusing one `requestId` per logical submission, and records a
    per-user ledger (`server/reports/load1000/ledger-*.json`).
  - `npm run verify:load1000` → `server/scripts/verify-1000.mjs`: read-only
    reconciliation of the newest ledger against the database (34 check groups,
    including a 100-user stratified deep sample).

## Findings

Ordered by severity. F1–F4 are the ones worth acting on; the rest are polish.

- **F1 — HIGH (availability): the connection pool can starve PostgreSQL entirely,
  and burst load surfaces as 500s.** `config.ts` allows `DB_POOL_MAX` up to 100 and
  the local server ran it against stock PostgreSQL `max_connections=100`: during the
  run the pool consumed every connection — external clients got
  `FATAL: sorry, too many clients already`, and `/ready`, migrations, and monitoring
  would be locked out the same way. Queued acquisitions then tripped the hardcoded
  5 s `connectionTimeoutMillis` (`server/src/db.ts:9`, not configurable), which is
  what turned the 1000-way register barrier into 634 HTTP 500s with the naive
  client. Size the pool below the server's `max_connections` (and per-replica),
  and consider making the acquisition timeout/behavior deliberate (queue with
  backpressure, e.g. 503, instead of 500).
- **F2 — MEDIUM (spend control): client aborts defeat the `assess-ip-daily`
  budget.** With `skipFailedRequests` (`server/src/rate-limit.ts:144,162`), an
  early-aborted assessment gets both rate-limit hits refunded, yet nothing cancels
  the running pipeline — S3 download, ffmpeg, Whisper, GPT, and the DB commits all
  complete (`assess.ts:146-248` has no disconnect handling). The anti-account-cycling
  per-IP ceiling becomes register-limiter × per-account cap instead of the intended
  300/day. The `assessment_usage` reservation is deliberately kept in this case, so
  the two accounting layers disagree; daily caps still bound total spend.
- **F3 — MEDIUM (cross-stack): the app never honors the contracted
  `503 + Retry-After` assess backpressure.** No reference to 503/Retry-After exists
  in `app/src`; a 503 submit is not in the Recorder's `definitelyRejected` list
  (`app/src/components/Recorder.tsx:1133-1134`), so users are routed into the
  interrupted-submission recovery flow instead of a timed retry. Production default
  `AI_MAX_CONCURRENCY=10` makes 503s routine under ordinary concurrency (this run
  saw 2,572 with the cap at 100 — absorbed cleanly only because the test client
  retries). Add explicit 503 handling: wait `retryAfterSeconds`, resubmit the same
  `requestId` (the server abandons the idempotency row, so resubmission is safe).
- **F4 — MEDIUM (app UX): a deterministic 409 strands S3-mode users in
  "recovering" for ~5 minutes.** Same-question resubmission or a second device
  advances state → `409`; recovery polls 404 forever and S3 resubmission repeats
  the 409 until the lease expires (`Recorder.tsx:432-439,578-586,627-662`;
  server abandons the request row on 409, `diagnostic.ts:117,366`). Treat
  question-mismatch/already-in-progress 409s as terminal-with-message instead.
- **F5 — LOW:** audio-inspection timeouts are reported as `415 Invalid or
  unsupported audio file` (`audio-inspection.ts:536-541`), blaming the file for a
  saturated host; should be a retryable 503/504 like the slot-acquisition path.
- **F6 — LOW:** mid-request client disconnect unlinks the temp audio under the
  running handler (`upload.ts:123-131`, `audio-upload.ts:322-323`) → spurious
  500/415 log noise; response is undeliverable anyway.
- **F7 — LOW (app):** a stale `/diagnostic/next` refetch (focus after >5 min)
  wipes the unacknowledged answer card (`app/src/app/diagnostic.tsx:63-77`).
- **F8 — LOW (app):** `practice/attempt.tsx` doesn't reconcile the cached question
  after a failed English attempt, unlike `practice/index.tsx:51-68` — stale
  "New word"/counts until the next canonical advance.
- **F9 — LOW (app):** submit-time tombstone mismatch can silently discard a
  brand-new recording (`Recorder.tsx:987-1001` + `startRecording` not checking for
  an unresolved pending record).
- **F10 — LOW (app, dev-only web):** Chrome's `audio/webm;codecs=opus` blob type
  trips the server's exact-MIME filter → 415 in direct mode
  (`app/src/lib/api.ts:305-308` vs `server/src/upload.ts:70-78`); re-wrap the blob
  with the descriptor type to make it deterministic.
- **F11 — LOW (schema):** `attempts` has no `UNIQUE (user_id, question_id, context,
  attempt_no)` and no `request_id` column (attempt↔request linkage exists only via
  `assessment_requests`); per-IP rate-limit counters are a single-row
  serialization point (held 20k+ increments in this run, but it is the hottest row
  in the schema under one-IP load).

## Follow-up: fix verification pass (same day, second working tree)

A subsequent working tree (agent-authored fixes, reviewed and completed here)
addressed the findings. Status per finding, verified by reading the code and
re-running every gate plus the full 1000-user load:

| Finding | Status | Evidence |
|---|---|---|
| F1 pool starvation / 500 storm | **Fixed (completed here)** | The tree added 503+Retry-After shedding for pool-acquisition timeouts (`middleware.ts`) and counter-store brownouts (`postgres-rate-limit-store.ts`, fail-closed). This pass added the remaining guardrail: a boot-time error log when `DB_POOL_MAX` leaves fewer than 3 server connections (`index.ts`), plus `.env.example` sizing guidance. Load v3: **zero 5xx** (3,582 contracted 503s honored by clients); boot guard observed firing with `DB_POOL_MAX=100`. |
| F2 abort refunds defeat `assess-ip-daily` | **Fixed (completed here)** | The tree added the `onCapacityReserved` hook + `requestWasSuccessful` predicate (post-reservation ≥400s keep the hit). Verified residual leak: express-rate-limit's close handler refunds aborted requests **unconditionally** (dist source, `index.cjs:1026-1028` — the predicate is finish-path only), so the abort vector was still open. This pass added `assessAbortGuard` (`rate-limit.ts`), mounted after the assessment limiters on all three assess routes, which re-spends both hits when an abort follows the reservation. Unit-tested. |
| F3 app ignores 503+Retry-After | **Fixed (this pass)** | `ApiError.retryAfterSeconds` plumbed from the bounded body field/header (`api.ts`); Recorder resubmits the **same requestId** up to 3 times honoring the delay (`Recorder.tsx`), then falls back to recovery. Regression tests cover both paths. |
| F4 409 strands S3 users ~5 min | **Fixed (this pass)** | A resubmission 409 is genuinely ambiguous (the requestId row may have appeared after the 404 absence checks), so the Recorder now defers the decision one status read: still-404 → terminal with a clear message; processing/completed → keep polling (existing pinned test proves the in-flight case still resolves). |
| F5 inspection timeout → 415 | **Fixed (this pass)** | `verifyAudioDuration` maps the timeout kind to a retryable 503 (`audio-inspection.ts`); tests updated, incl. a real hanging-probe integration test. |
| F6 disconnect-unlink race noise | **Fixed (this pass)** | `errorHandler` drops the response quietly when the client is already gone. Detection uses the socket — `req.destroyed` is unsafe (true after any fully-consumed multipart body; caught by the suite when injected-failure tests started returning bare 200s). |
| F7 diagnostic refetch wipes card | **Fixed (this pass)** | The `/next` effect skips while an unacknowledged result is on screen (`diagnostic.tsx`); regression test proven to fail without the guard. |
| F8 attempt-screen cache reconciliation | **Fixed (by the tree)** | `applyFailedAttemptToQuestionCache` shared by both screens (`practice-flow.tsx`). |
| F9 tombstone race drops fresh take | **Documented wontfix** | A blocking guard in `startRecording` was implemented here and **reverted**: it inverted pinned invariants (recording start must not await the SecureStore read; delayed-read suppression tests). The harmful resolution path (old result delivered) discards the take via the navigation blur lifecycle regardless, no double-charge occurs, and the user always sees the committed outcome. Residual is a narrow, self-healing UX edge. |
| F10 web 415 on codecs suffix | **Fixed (by the tree)** | Blob base-MIME descriptor map incl. Safari MP4 (`api.ts`). |
| F11 schema hardening | **Rejected with evidence** | `UNIQUE (user_id, question_id, context, attempt_no)` is invalid by design: `attempt_no` resets to 1 after a pass, so legitimate retention re-attempts would violate it. The `request_id` forensics column stays out as low value; `assessment_requests` already links attempts. |
